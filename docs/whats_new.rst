figwig files
------------

	- Dense float tracks read and write faster. A runs chunk, which the writer chooses for conservation and fold-change tracks whose values hold for a base or two, decoded at 70 ns a change, since each change took the window's row again and called the per-run kernel; the common case, a window set or added into its row, now fills the row in place at 3 ns a change. A read of a chromosome of large chunks is planned as at least two batches per thread, where one batch of 32 MB held the chunks of a whole chromosome of three float tracks and 32 threads split its windows, each part inflating the chunks again, and a write call of dense tiles is cut into up to one task per thread of at least 4 MB, where it was two tasks whatever the pool's size. Three phyloP and phastCons tracks over chr22, 8,192 windows of 2,048 bp: 1.95 s, 0.42 s and 0.21 s on 1, 8 and 32 threads before, 0.50 s, 0.07 s and 0.03 s after, against 0.80 s, 0.12 s and 0.11 s from the bigWigs; writing them on 32 threads takes 0.19 s where it took 0.39 s.

	- The format is specified on ``docs/format.rst``: every byte of a version 1 file, what a reader must check, what the writer produces, the limits, and an annotated dump of a small file. ``tests/format_reference.py``, a reader written from the page with numpy and zlib and nothing from the package, reads files written in every layout the format has and ``tests/test_format.py`` compares every table, record and value with the package's, and ``docs/figwig.ksy`` is a Kaitai Struct definition of the same layout, whose compiled parser ``tests/test_kaitai.py`` runs over the same files. Two things changed on the way to it: the statistics table's minimum and maximum are those of a track's nonzero bases, where before the 0 of bases without a value was included, so a track of positive values had a minimum of 0; and each group's summary stream carries a CRC-32, as its zoom streams did. Version 1 is frozen by the page.

	- A new file format, the figwig file (``.fw``), holds the per-base values of any number of tracks over one genome in one file, with a JSON record of attributes for each track and the name of the reference genome, and is read many windows at a time from any subset of its tracks into one array of shape ``(windows, tracks, width)``, in the type the tracks were written as. ``FigWigReader``, ``read_figwig``, ``FigWigWriter`` and ``write_figwig`` mirror the bigWig API with a ``tracks=`` argument; ``FigWigReader.select(**attributes)`` gives the indices of the tracks whose records match, ``stats`` each track's sum, nonzero bases, minimum and maximum, and ``written_by`` the figwig that wrote the file. This is version 1 of the format; a reader refuses a file of a later version, or one that sets a ``required`` feature bit it does not know, saying a newer figwig wrote it.

	- Layout. Every track lies on one grid of ``tile`` bases, so a window's tiles are found by division, and the tiles of a group of tracks are one chunk: nothing when every value is zero, and otherwise dense, sparse (nonzero bases, so that a read of some of a group's tracks steps over the others'), runs (the bases where the value changes, for tracks of bins or fold change) or a per-tile matrix of the tracks present, whichever is smallest, in the narrowest element type that holds the values exactly, with a ``one`` type that stores no values when every nonzero value is 1, as single-cell cut sites are, and a float64 type that keeps an integer above 2**24 exact beside a fraction. Chunks are compressed with zlib or libdeflate on ``n_jobs`` threads, or stored as they are when deflate would grow them; ``level=0`` writes an uncompressed file. The index holds only the tiles with values, so a group costs bytes for its data rather than per genome, and a file of 100,000 single-track groups opens in a tenth of a second.

	- Two orders. ``order='positions'`` (``'csc'``), the tile layout above, reads windows across many tracks; ``order='tracks'`` (``'csr'``) stores each track's nonzero bases in blocks per chromosome, for reading a few tracks over the genome; ``figwig reorder`` rewrites a file in the other order, and may write over its input.

	- Reads. ``read(..., sparse=True)`` returns the nonzero bases as a ``SparseWindows`` of entries, ``labels=`` sums the tracks per label in the read, which turns cells into pseudobulks, ``bins=`` sums each window per bin of bases, ``read_entries(tracks, chroms)`` returns every nonzero base of tracks over chromosomes, and ``channels="channel", items="read"`` arranges the tracks read by two attributes into ``(windows, items, channels, width)``, for reads, cells or channels as tracks. A read of mixed tracks comes back in the narrowest type that holds every track exactly, sums of integer tracks in float64, and a dense read whose output would pass 8 GiB raises instead of allocating it. A read uses one thread per 64 chunks it touches, up to ``n_jobs``, and keeps its pool between reads.

	- Sums. ``FigWigReader.sums(chroms, starts, ends, tracks=None, nan='propagate', paired=False)`` sums intervals of any lengths, such as peaks or genes; ``nan='skip'`` leaves NaN bases out and ``nan='count'`` gives the bases that are not NaN, so a mean over covered bases, as pyBigWig and deepTools give it, is the one over the other on a file whose uncovered bases are NaN; ``paired=True`` sums interval i over track i alone, for reads whose spans are their own tracks. ``tile_sums(tracks, chroms, level=0)`` gives each track's sum over every tile from the file's summaries, kept while they take at most 256 MB, without decoding a chunk, and ``tile_sums(level=k)`` the zoom levels a file written with ``zooms=`` (``bw2fw -z``, ``bam2fw -z``) keeps, each 4 times coarser than the last, which ``FigWigReader.zooms`` lists and ``info`` prints.

	- Writes. ``write`` takes windows or intervals of whole groups, and ``write_sparse(chroms, positions, tracks, values)`` takes nonzero bases as entries, the form of single-cell cut sites and of a sparse matrix's triplets; both encode and compress on the ``n_jobs`` threads, so that 512 count tracks over chr1 write in 38 s on 8 threads. A track's ``dtype`` may be declared (``uint8`` to ``uint32``, ``int8`` to ``int32``, ``float32``, ``float64``) or inferred; a float32 track keeps float32's rounding, a value beyond float32 raises unless the track is float64, a 64-bit integer beyond 2**53 and an infinite value are refused before anything is written, and -0.0 is 0. The file is written beside its path and moved there at ``close``, so a failed write, a writer never closed (which warns), or a conversion over its own input leaves the path as it was.

	- Adding tracks. ``FigWigWriter(path, None, tracks, append=True)`` adds tracks to the file at the path in place, under the file's lock, writing the new chunks after its end and the header last, so that the cost is the new chunks and a writer that fails or is killed leaves the file readable as it was. ``FigWigWriter.add_file(path)`` and ``figwig merge`` copy every track of another file written with the same chromosomes, tile, level and order, and ``figwig bw2fw --append`` adds bigWigs to a figwig file.

	- Integrity. Every chunk's CRC-32 is kept and ``FigWigReader(path, verify=True)`` checks each chunk read against it; the header, the tables and each index record carry CRC-32s checked at open, every count is bounded against the file before its bytes are asked for, and every pointer of a chunk is checked before it is read by, so a damaged, crafted or truncated file raises ``ValueError`` rather than a ``MemoryError`` or a crash. The reader checks on every read that the file at its path is the one it opened, so a file replaced by a conversion raises instead of reading with a stale index, while a reader keeps reading through an append in place.

	- Reading onto a GPU. ``FigWigReader.read``, ``sums`` and ``read_figwig`` take ``device="cuda"`` (or ``"cuda:N"``, or an index) and land their output in that GPU's memory as a ``cupy.ndarray``, which PyTorch, JAX, TensorFlow and CuPy take without a copy through DLPack (``torch.from_dlpack(y)``); the new ``cuda`` extra adds cupy. Sparse tracks are scattered on the device from their entries, dense tracks copied from a pinned host buffer kept on the reader, and the stream is synchronized before the array is returned. Without ``device``, ``out=`` may be a numpy view of a pinned torch tensor.

Converters and commands
-----------------------

	- ``figwig bam2fw`` and ``figwig bam2bw`` check each BAM's header against the sizes before reading: a chromosome both name must have one length, and the BAM must share a chromosome with the sizes, or ``bam2fw`` refuses the file with both lengths, or both sides' chromosomes, named, and ``bam2bw`` says the same on stderr and goes on, as bam2bw 0.5.1 takes a sizes file of other chromosomes or shorter lengths and reports the reads it leaves out. An hg19 BAM against hg38 sizes placed every read at its hg19 position in a file of hg38 lengths, with nothing said but the few reads past the shorter chromosome ends, and sizes of other names dropped every read and wrote a file of zeros. The reader is not touched; the check opens the header through pysam.

	- ``figwig bw2fw -s`` refuses a bigWig that shares no chromosome with the sizes file, naming both sides' chromosomes, where it wrote an empty file with a warning: a sizes file of another assembly, or of names without the ``chr`` prefix the bigWig has, dropped every value and exited 0. ``figwig bam2fw`` and ``figwig bam2bw`` print a message for an input that is not a BAM, is cut short or does not exist, where pysam's traceback escaped. An empty track survives the round trip through ``fw2bw`` and ``bw2fw``: ``BigWigReader`` opens a bigWig without a data index, which ``BigWigWriter`` writes for a track with no values and ``fw2bw`` for an empty track, and reads every window as ``missing``, where it refused the file as unreadable.

	- ``figwig bw2fw`` writes bigWigs as the tracks of one figwig file, named after their files or by a metadata table whose other columns become the tracks' attributes; an interval whose value is NaN stays NaN, and ``--missing nan`` writes the bases no interval covers as NaN too, for methylation and conservation tracks whose zeros are measurements, recording the convention in the file. ``figwig fw2bw`` writes a figwig file's tracks back as bigWigs with such a table, so the two round-trip names and attributes. ``figwig bam2fw`` takes what ``figwig bam2bw`` takes and writes each input file as its own pair of stranded tracks, or one unstranded track; ``--barcode-column N`` writes a fragments file as one track per cell instead, named by the barcode in column ``N``, every cell of a file in one group, scanned in BGZF units on the ``-p`` threads at 8 bytes per fragment end, with ``--cells`` listing the cells to keep and their attributes, such as a cell type, and ``--groups`` the cells per group (every cell of a file in one otherwise, up to the 2**29 values a chunk holds); a truncated gzip or BGZF file is refused with a message. The 257.6 million fragments of the 10x PBMC experiment become its 10,246 called cells in 9 s on 8 threads, 5.5 s on 32 and 60 s on one, against 140 s for the pandas recipe the skill gave before and 217 s for SnapATAC2: the scan, the sort and decoding of each chromosome's keys, the encoding, the compression and the checksums all run on the threads, the entries reach the writer in the order its encoders take and in the types it takes, so it makes no pass over them, and the entries encoder visits only the tracks a tile touches, which a group of thousands of cells feels. Two changes reach every ``write_sparse`` call: a batch's chunks are checksummed in one numba call rather than one ``zlib.crc32`` call per chunk, and a batch holds at least a million entries, bounded by the tiles whose chunk headers fit the encoder's buffer. ``figwig info`` prints what a file holds, and ``-b`` the bytes its chunks, tables and unused space take. Every command refuses to write over an output that exists unless ``-f`` is given (``--force`` for ``bam2fw``), writes its output beside its path and moves it into place when complete, and prints a message rather than a traceback for a missing input.

Reading
-------

	- The bigWig reader takes a file whose index leaves lie in natural chromosome order, chr1, chr2, ..., chr10, where the ids run chr1, chr10, chr2, by sorting the leaves; two bigWigs of the test collection were refused as unsorted where pyBigWig read them. ``BigWigReader.read`` and ``read_bigwig`` take ``keep_nan=``, with which an interval whose value is NaN reads as NaN rather than ``missing``.

	- ``read`` and ``read_bigwig`` take ``engine``: ``'auto'``, the default, ``'zlib'`` or ``'isal'``. ``'auto'`` inflates data blocks with ISA-L where python-isal 1.8 or later is installed (the new ``isal`` extra; the ``bam2bw`` extra installs it too) and with zlib otherwise. ISA-L is called through two functions python-isal's extension exports, from the numba kernel without the GIL, as zlib's ``uncompress()`` is, so no compiler is needed; the kernel writes ISA-L's inflate state at the offsets of ISA-L 2.31.1, so it is used only with that version, on 64-bit platforms, and only once one known block inflated through it has given zlib's bytes. Every engine gives the same values, and the reading tests run under both. Reading the benchmarks' ATAC-seq and DNase-seq bigWigs takes 1.3 to 1.5 times less on 1 to 8 threads (1.0 to 1.4 on a first read in a fresh process). Thanks @YaoxiangLi!

Writing
-------

	- ``_zoom_records``, the kernel that summarizes items into one zoom level's records, holds the open record in locals and stores it back when it returns, instead of writing it to the level's state arrays for every item. Zoom levels are summarized on different threads at once, and their small state arrays can share a cache line, which makes the kernel many times slower in the processes where the arrays happen to be allocated next to each other. The files written are unchanged. Thanks @YaoxiangLi!

	- With threads, ``BigWigWriter`` plans each batch of items as data blocks on a thread of its own, encodes and compresses the blocks on the pool, and folds the batch into the file's summary in file order on another thread, so the calling thread only takes the next call's values; before, it laid every batch out itself, which was the limit with libdeflate from 8 threads on. Sorted input with valid values, the common case, is confirmed in one compiled pass instead of the masks and differences of the general checks, which now run only when that pass finds something and raise the same errors in the same order. Threaded writers take batches of 786,432 items instead of 1,048,576, so they hold less input at once. The files written are unchanged, byte for byte. Writing the benchmarks' tracks with libdeflate and no zoom levels on 8 threads takes 1.4 to 1.5 times less, other settings up to 1.2 times less, and peak memory without zoom levels falls by 3 to 12%. Thanks @YaoxiangLi!

Claude Code skill
-----------------

	- The skill covers figwig files, in ``references/figwig-reading.md``, ``figwig-writing.md`` and ``converters.md``, and ``references/recipes.md`` walks through whole jobs: a training set from many bigWigs or BAMs, genome-wide predictions, a single-cell file, summaries over peaks, a lossless signal round trip and reads as tracks. The router routes by task and by symptom to the operation to use, every error message is in ``references/errors.md``, and the machine-bound timings are gone in favour of the rules they supported and a snippet to measure with. Tests
-----

	- The test suite runs in a quarter of the time: ``figwig bam2bw``'s tests run the command in the test process rather than one subprocess each, which cost a second of imports per test, the damage test flips every 61st byte of the chunks rather than every fifth (the header, tables and index keep every fifth), and ``pytest-xdist`` is in the dev extra for ``uv run pytest -n 8``. CI keeps numba's cache between runs, keyed on the hash of the four files that hold kernels with no fallback, since numba does not notice a change to a constant or kernel used from another file, and runs the tests on every core of the runner: a job that compiled every kernel specialization from scratch, which was most of its time, now does so only for a commit that touches a kernel file.


Version 0.1.0
=============

Reading
-------

	- Initial release. ``BigWigReader(path).read(chroms, starts, width, out=None, n_jobs=8, missing=0.0)`` reads the per-base values of many windows of one width into a float32 numpy array of shape ``(n, width)``, on up to ``n_jobs`` threads, or one per CPU with ``n_jobs=-1``. ``read_bigwig`` does the same in one call, and given a list of bigWigs reads them all into one array of shape ``(n, len(bigwigs), width)``, with every file's batches on one pool of threads.

	- The values are those pybigtools' ``values(chrom, start, end, missing=missing)`` gives: ``missing``, 0 unless given, where no interval covers a base or an interval's value is NaN, and NaN past the end of a chromosome. A window on a chromosome that the file does not have, which writers leave out when it has no data, is ``missing`` throughout, and a warning names the chromosomes.

	- bedGraph, varStep and fixedStep sections are read, compressed or not, including pyBigWig's fixedStep blocks whose index entries overlap by a few bases. A file or data block that figwig does not read, such as a bigBed, a big-endian bigWig, a corrupt or truncated index, or a block with overlapping intervals, raises a ``ValueError`` that says what it found.

	- A ``BigWigReader`` can be read from several threads at once and pickled, so it can be part of a PyTorch Dataset read by DataLoader workers under any start method.

	- The reader began inside tangermeme's ``extract_loci`` (tangermeme #107).

Writing
-------

	- ``write_bigwig(paths, chrom_sizes, chroms, starts, values, ends=None, missing=0.0)`` writes what ``read_bigwig`` reads: windows on any chromosomes, in any order, with values of shape ``(n, width)`` for one file, or ``(n, len(paths), width)`` for several, channel ``i`` to the ``i``-th file. With ``ends``, it writes intervals and one value for each. Bases and intervals whose value is ``missing`` or NaN are left out, so that reading with the same ``missing`` gives the values back, and bases past the end of a chromosome, which ``read_bigwig`` gives as NaN, are accepted there. ``BigWigWriter(path, chrom_sizes, zooms=10, level=6, engine='auto', n_jobs=8)`` writes the same values a batch at a time with ``write(chroms, starts, values, ends=None, missing=0.0)``, each call after the last. Values are converted and laid out about a million at a time, however many one call holds. Data blocks are compressed on up to ``n_jobs`` threads by zlib's ``compress2()``, or by libdeflate when the ``deflate`` package is installed (the new ``fast`` extra), both called without the GIL, except on Windows, where neither library can be loaded and Python's zlib module compresses the blocks; ``engine='isal'`` uses ISA-L. Zoom levels are built when the writer is closed.

	- Each window, or each 65,536 bases of a wider one, is written as whichever section type takes it in the fewest bytes: fixedStep for runs of bases, varStep for scattered bases, or bedGraph for stretches of one value. Intervals are written as bedGraph, as they are given.

	- Written files are laid out as libBigWig, pyBigWig's writer, lays them out, and a file of intervals, or of single bases as windows of width 1, written with ``missing=numpy.nan``, without zoom levels and with zlib at level 6, is pyBigWig's byte for byte. Where libBigWig writes a wrong value, figwig writes the correct one: the header's maximum when the first value is the largest or no value is positive, the end of the last fixedStep block of each call, which libBigWig puts 6 bases past it, and the sum and sum of squares of the last zoom record of each zoom block, which libBigWig leaves at 0. libBigWig's empty blocks are not written, and zoom levels go on past a level that is no smaller than the one before it, where libBigWig stops.

figwig bam2bw
-------------

	- ``-c/--coverage`` counts every aligned base of each read, the CIGAR's M, = and X runs (a deletion or a skipped intron is not covered, as pysam's ``get_blocks()`` and deepTools' ``bamCoverage`` count them), or every base of each BED/tsv interval, in place of one end, on the same keys, threads and readers as the end counts: each block is two events on a doubled coordinate line whose running sum is the coverage, written as intervals of one value. ``-ps`` and ``-ns`` move a read's first base and its end, ``-r`` divides by the reads that start inside their chromosome, and the bases a read extends past a chromosome's end are the discarded entries. ``figwig bam2fw -c`` writes the same coverage as runs, each track its own group. On the 2.4 GB ATAC-seq BAM the bigWig holds the same value at every one of its 3.1 billion bases as ``bamCoverage --binSize 1``, in 3.4 s on 8 threads against deepTools' 14.9 s, and 11.9 s on one against 46.2 s; on ten more experiments, single- and paired-end ChIP-seq, ATAC-seq, DNase-seq, PRO-cap, RNA-seq, CUT&RUN, MNase-seq, ChIP-nexus on mm10 and PacBio RNA long reads, from 40 MB to 2.4 GB, the two agree at every base and figwig is 3 to 8 times faster.

	- ``figwig bam2bw``, a command, is bam2bw 0.5.1 with the same arguments, outputs and messages, reading files as the winner of a speed search over bam2bw's code reads them, a BAM file with libdeflate and a numba kernel on the ``-p`` threads and a BED/tsv file with a numba kernel, and writing the counts with ``BigWigWriter``, with libdeflate at level 1. Its bigWigs hold bam2bw's entries, but not its bytes, and ``-z`` writes figwig's zoom levels. ``-p`` is a number of cores: files are read one after another, each on every core, and files read on one thread (SAM, ``--mate_pairs``, remote files, gzipped BED/tsv files that are not BGZF) by a pool of processes alongside them. It needs the new ``bam2bw`` extra. A BAM file's keys, one per counted read end, are counted a group of chromosomes at a time while the file is read and then dropped, so that for a coordinate-sorted BAM the array that holds them is the size of its largest chromosome's rather than the whole file's.

Claude Code skill
-----------------

	- ``figwig install-skill`` installs figwig's Claude Code skill, which teaches a coding agent to read and write bigWigs with figwig and to convert reads with ``figwig bam2bw``: the signatures and shapes, the rules a write follows, the error messages and their causes, and the measured gain from threads. It copies the skill into ``~/.claude/skills/figwig``, or ``-d DIRECTORY/figwig``; ``--symlink`` links to the package's copy instead, and ``--force`` replaces an installed copy, which an upgrade of figwig needs to pick up a changed skill.

Platforms
---------

	- Tested on Linux with Python 3.10 to 3.14, and on macOS and Windows with Python 3.10 and 3.13. On Windows, which has no ``os.pread`` and where neither zlib's library nor libdeflate's functions can be loaded, blocks are read by seeking the file, and decompressed and compressed by Python's zlib module, with the same values. ``figwig bam2bw`` runs on Linux and macOS, since pysam does not support Windows.
